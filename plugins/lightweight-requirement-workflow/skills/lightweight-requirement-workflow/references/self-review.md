# 需求自检

## 原则

先独立检查，再修复。不要因为自己生成了产物就默认其正确。报告保存为 `self_review.md`。

## 一致性检查

| 维度 | 核心判断 |
| --- | --- |
| 文档完整性 | 五份文档、SVG、HTML 和变更记录是否齐全 |
| 功能覆盖 | PRD 功能是否都有用户故事和验收标准 |
| 页面对应 | 用户路径是否有页面，页面是否有需求来源 |
| 异常场景 | 流程、PRD、故事和原型是否覆盖主要失败分支 |
| 非功能需求 | 是否量化或明确留给技术评审 |
| 术语与知识库 | 是否与已有产品术语和决策冲突 |
| SVG/HTML | 页面、状态、文案和操作是否与文档一致 |
| 隐私与数据 | 演示、日志和埋点是否包含不必要敏感信息 |

## 产品风险检查

对承重假设逐项写出：成立理由、Fails if、最便宜测试、Kill criterion、处理建议。重点攻击身份/所有权、状态失效、数据口径、生产链路、异常恢复和外部依赖。

## 分级

- `FAIL`：阻断评审或会造成错误用户、错误数据、隐私泄露、主流程不可用。
- `WARN`：不阻断，但需要责任人、观察项或后续技术决策。
- `PASS`：有证据支持，不是“看起来没问题”。
- `SKIP`：用户明确跳过对应产物。

报告列出问题、证据、影响、建议及产品决定。FAIL 修复后重新检查，最多三轮。用户可以接受 WARN，但不能用一句“风险已知”掩盖未定义的责任和监控方式。
