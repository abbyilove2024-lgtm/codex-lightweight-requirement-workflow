# 文档套件

## 生成顺序

严格按以下顺序生成，后项引用前项：

1. `flowchart.md`
2. `prd.md`
3. `user_story.md`
4. `prototype.md`
5. `review.md`

所有文档顶部包含变更记录。功能使用稳定编号，例如 `F-001`；用户故事使用 `US-001`；页面使用 `P-001`。更新时只改受影响章节并递增版本。

## flowchart.md

- 使用 Mermaid 描述主流程和主要异常分支。
- 覆盖角色、入口、状态转换、失败回退和终止状态。
- 流程节点使用 PRD 中将采用的术语。

## prd.md

至少包含：背景与问题、目标、用户与场景、范围、详细设计、业务规则、状态与异常、字段、非功能需求、埋点、依赖、发布计划、不在本期范围。

- 每个范围内功能都在详细设计中展开。
- 优先级使用 P0/P1/P2。
- 性能和兼容要求必须可验收；未知数字标记待技术评审，不拍脑袋。
- 描述需要什么，不擅自决定数据库、缓存或框架。

## user_story.md

每个 P0/P1 功能至少有一个用户故事：

```text
作为 {角色}，我想要 {行为}，以便 {价值}。
```

每条至少包含正常和异常 Given-When-Then 验收标准，并标注优先级和关联功能编号。按 INVEST 原则检查粒度与可测试性。

## prototype.md

列出页面、SVG 文件、HTML 状态/锚点及对应用户故事。每页写清布局、元素、交互、默认/加载/空/错误/成功/禁用等适用状态。这里只定义结构和行为，不提前决定高保真视觉。

## review.md

建立评审概览、议题、待办、风险和结论。未实际开会时结论必须为“待评审”，不得伪造参与人、负责人或日期。正式结论只允许：通过、有条件通过、需重新评审。

## 套件一致性检查

- PRD 每个功能有用户故事承接。
- 用户故事的核心场景有页面或明确说明无需页面。
- 页面清单、流程状态、字段和文案术语一致。
- 异常分支在流程、PRD、验收标准和原型状态中相互对应。
- 交叉链接使用相对路径且目标存在或明确标注待生成。
